## The shape of the whole thing

Four phases, each a separate translation unit, joined by one driver:

```
lexer.l ──tokens──▶ parser.y ──AST──▶ semantic.cpp ──▶ executor.cpp ──▶ output
   │                   │                                    │
   └── Flex            └── Bison                            └── CSV / UniProt
                                  pipeline.cpp orchestrates all four
                                  main.cpp / wasm_api.cpp choose the input
```

The single most important structural fact: **`pipeline.cpp` contains the phase
sequence exactly once**, and the two front ends differ *only* in where the
lexer reads from. That is why the browser and the CLI cannot disagree.

Roughly 2,300 lines in all: about 1,700 are the compiler proper (1,376 lines
of hand-written C++17 plus 336 of Flex and Bison specification), and the rest
is the page, the build and CI.

## Phase 1 — `lexer.l`

72 lines. Turns characters into tokens.

### Prologue (lines 13–24)

```c
#include "ast.h"
#include "parser.tab.hpp"
int lex_errors = 0;
```

`parser.tab.hpp` is generated by Bison and defines the token constants
(`LOAD`, `FIND`, …) and the `yylval` union — so the lexer must be compiled
*after* Bison has run. The Makefile encodes that dependency.

Two options matter:

- `%option noyywrap` — there is no "next file" after the input ends, so we
  don't have to link `libfl` just to supply `yywrap()`.
- `%option yylineno` — Flex maintains `yylineno` for us, which is what every
  error message uses.

`lex_errors` counts lexical failures. Flex's default behaviour on an
unrecognised character is to echo it and continue; we want the run to fail
instead, so we count and check later.

### Rules (lines 28–71)

**Ignored input (28–29).** Whitespace including newlines, and `//` comments.
Because newlines are skipped, a statement can span lines freely.

**Keywords (31–44).** One literal rule per keyword. All fourteen are listed
here, uppercase only.

**Operators (46–51).** Note the ordering: `>=`, `<=`, `!=` come *before* `=`,
`>`, `<`. Flex prefers the longest match, so `>=` would win anyway — but
listing them first makes the intent explicit and is robust if the rules are
ever reordered.

**String literals (53–57).**

```c
\"[^\"]*\"    { yylval.strval = strdup(yytext + 1);
                yylval.strval[strlen(yylval.strval) - 1] = '\0';
                return STRING; }
```

The pattern is "quote, any run of non-quote characters, quote". `yytext + 1`
skips the opening quote and the assignment overwrites the closing one with a
terminator — so the parser receives the string's *contents*, not its
punctuation. `strdup` allocates; the parser frees. That the pattern excludes
`"` is why the language has no escape sequences.

**Numbers (59).** `atof` into `yylval.numval`. Stored as a `double` because
the union needs one numeric type; the parser converts back to an integer where
that's what's meant.

**Identifiers (61).** The classic `[A-Za-z_][A-Za-z0-9_]*`. This rule is
*last* among the word-shaped rules, which is the whole reason `LOAD` is a
keyword and `loaded_at` is an identifier: on a tie in match length, Flex takes
the rule that appears first.

**The catch-all (63–71).** Any character no other rule matched. It formats a
message with the line number, pushes it onto `g_parseErrors` so `--json` (and
the web UI) can report it, prints it to stderr, and increments `lex_errors`.

> **Reviewer question — "why does the error go to two places?"** The
> `fprintf` is for a human watching the terminal, live as it happens. The
> `push_back` is so the same message can be embedded in the JSON document that
> the browser renders. Same text, two audiences.

## The AST — `ast.h`, `ast.cpp`

### `ast.h` (108 lines) — the data the parser builds

Enumerations first: `StmtType` (`LOAD`/`FIND`), `LoadSource`
(`FILE`/`UNIPROT`), `CompareOp`, `SortDir`, `OutputKind`
(`DEFAULT`/`DISPLAY`/`COUNT`).

```cpp
struct ValueLiteral { std::string text; bool isNumeric = false; };
```

The right-hand side of a condition. `isNumeric` records **which token the
lexer produced**, not a guess made by re-reading the text. This one field is
what makes `length = "300"` a type error rather than a silent success.

```cpp
struct Condition { std::string field; CompareOp op; std::string value; bool isNumeric; };
using AndGroup    = std::vector<Condition>;
using WhereClause = std::vector<AndGroup>;
```

**`WhereClause` is disjunctive normal form** — an OR of AND-groups. `a AND b
OR c` is stored as `{{a, b}, {c}}`. The record matches if *every* condition in
*any one* group matches. Two design payoffs: the parser can build it directly
as it reduces (no tree to flatten afterwards), and the executor's matcher is
two nested loops instead of a recursive walk.

`SortSpec` and `OutputSpec` bundle the multi-part optional clauses so each can
travel through the parser as a single semantic value.

`Statement` (lines ~63–100) is a flat struct holding the union of everything
any statement needs, with `type` saying which fields are meaningful. A variant
or inheritance hierarchy would be more precise; for two statement kinds and a
project of this size, a flat struct with a discriminator is easier to read and
to print.

Finally the two globals the parser fills:

```cpp
extern Program g_program;                      // the parsed statements
extern std::vector<std::string> g_parseErrors; // phase 1+2 diagnostics
```

Globals because that is Bison's calling convention — `yyparse()` takes no
context argument and returns only a status code.

### `ast.cpp` (77 lines) — the pretty-printer

`compareOpToString` maps the enum back to source text.

`printWhere` (lines 20–33) renders the DNF back into readable form, joining
groups with `OR` and conditions with `AND`, and re-quoting string values so
the printed AST reads like the input.

`printProgram` (lines 37–77) walks the statements. It writes to a
`std::ostream&` rather than to `std::cout` — that is what lets `pipeline.cpp`
capture the AST into a string for the JSON document, which is what the web
page displays in its "Abstract Syntax Tree" panel.

> This function is the visible proof that parsing produced structure and not
> just a "no errors" verdict. Worth showing on screen during a demo.

## Phase 2 — `parser.y`

~264 lines. Tokens in, AST out.

### Prologue (lines 27–47)

Defines `g_program` and `g_parseErrors` (declared `extern` in `ast.h`), and:

```cpp
static const double kNoTop = -1.0;
```

A sentinel for "no `TOP` clause". Bison's `%union` cannot hold a
`std::optional`, so an absent numeric clause needs an impossible value; `TOP`
is later validated as positive, so `-1` can never be legitimate.

### The `%union` (49–61)

Every member is a pointer or a trivially-copyable enum. That is a hard
requirement — Bison stores semantic values in a C `union`, which cannot hold a
type with a constructor or destructor. `std::vector<Condition>*` is fine;
`std::vector<Condition>` would not compile.

### Declarations (63–78)

`%token` lists the terminals; `%type` gives each non-terminal its union
member. Getting these wrong is a compile error, not a silent bug, which is one
of the nicer things about Bison.

### `statement` (87–127)

Three productions:

- **`LOAD STRING`** — a file load.
- **`LOAD UNIPROT STRING top_opt`** — a live search, reusing `top_opt` for the
  fetch size.
- **`FIND IDENTIFIER search_opt where_opt sort_opt top_opt output_opt`** — all
  five optional clauses in one production.

Each action builds a `Statement` and pushes it onto `g_program`. The `$n`
values are the semantic values of the symbols; `free($2)` releases what the
lexer's `strdup` allocated, and `delete` releases what an earlier action
`new`ed. Ownership is hand-managed and each action frees exactly what it
consumes.

> **Reviewer question — "why is a fully optional clause list not ambiguous?"**
> Each optional clause begins with a distinct keyword (`SEARCH`, `WHERE`,
> `SORT`, `TOP`, `DISPLAY`/`COUNT`), and they can only appear in that order.
> With one token of lookahead the parser always knows whether to shift into a
> clause or reduce the empty production. `bison -Wall` confirms it: zero
> conflicts.

### The `WHERE` sub-grammar (139–178)

```
or_expr  : and_expr | or_expr OR and_expr
and_expr : condition | and_expr AND condition
```

Two levels of left recursion is the textbook way to give `AND` tighter
binding than `OR` without precedence declarations: an `or_expr` is a list of
`and_expr`s, and an `and_expr` is a list of conditions. The actions build the
DNF directly — `and_expr` accumulates one `AndGroup`, `or_expr` accumulates
groups into the `WhereClause`.

`condition` (166–177) copies the field, operator and value into a `Condition`,
carrying `isNumeric` across from the `ValueLiteral` — the line that makes type
checking possible.

### `value` (189–204)

The `STRING` branch tags `isNumeric = false`; the `NUMBER` branch tags it
`true` and formats the double back to text. The formatting exists so `300`
prints as `300` and not `300.000000`: whole numbers go through `%lld`, others
through `%g`.

### Remaining clauses (206–252)

`sort_opt`, `dir_opt` (defaulting to `ASC`), `top_opt` (defaulting to the
sentinel), `output_opt` (`DISPLAY` list, `COUNT`, or neither), and `id_list`
for `DISPLAY`'s fields.

### `yyerror` (tail)

Bison calls this on a parse error. It formats `Syntax Error at line N: msg`,
**pushes it onto `g_parseErrors`**, and prints it. Without the push, the JSON
output would only be able to say "Parsing failed" with no line number — which
is exactly the bug this line fixes.

## Phase 3 — `semantic.h`, `semantic.cpp`

160 lines. Parsing proves a program is *well-formed*; this proves it is
*meaningful*.

### The shared vocabulary (`semantic.h`)

```cpp
const std::vector<std::string>& proteinFields();
std::string toLowerField(const std::string& s);
bool isKnownField(const std::string& fieldLower);
bool isNumericField(const std::string& fieldLower);
```

These are exported deliberately: **the executor includes `semantic.h` and uses
the same four functions.** One list of attribute names, one definition of
"numeric", shared by the phase that validates and the phase that executes. If
an attribute is ever added, both phases learn about it from the same place.

### `validateProgram` (lines 42–129)

One pass over the statements, collecting *all* errors rather than stopping at
the first — a reviewer typing three mistakes should see three messages.

It carries one piece of cross-statement state:

```cpp
bool seenLoad = false;
```

which is how `FIND ... used before any LOAD` is detected. This is the only
check that depends on statement *order*, and it is the reason semantic
analysis exists as a separate pass rather than being folded into the parser's
actions.

For `LOAD` statements: a UniProt `TOP` must be positive and at most
`kMaxUniProtLimit` (500 — the API's per-page cap), and neither the query nor a
file path may be empty.

For `FIND` statements, in order:

1. `seenLoad` — is there any data?
2. Entity name must be `proteins` (compared case-insensitively).
3. For every condition in every AND-group:
   - the attribute must exist (else `continue` — there is no point
     type-checking an attribute that isn't real);
   - an ordering operator on a string attribute is an error;
   - a numeric attribute with a string literal is an error;
   - a string attribute with a numeric literal is an error.
4. `SORT BY` field must exist.
5. `TOP` must be positive.
6. Every `DISPLAY` field must exist.

> **Reviewer question — "why check both type directions?"** Checking only that
> `length` gets a number would let `name = 300` through, and the executor would
> then compare the string `"300"` against protein names — succeeding, silently,
> and wrongly. Errors that produce plausible-looking output are worse than
> errors that stop the run.

## Phase 4 — `executor.h`, `executor.cpp`

620 lines together — the largest component, and the only one that touches the
outside world.

### `executor.h`

```cpp
struct ProteinRecord { proteinId, name, organism, length, function, sequence };
struct QueryResult   { entity, kind, columns, rows, matched, returned };
struct ExecOptions   { cacheDir };
```

`QueryResult` separates `matched` (records passing the filter) from `returned`
(what survived `TOP`) so the output can say `10 of 42 matched`.

`ProteinRecord` is the common shape both data sources are normalised into — a
CSV row and a UniProt TSV entry become the same struct, which is why every
clause works identically against both.

### Text utilities (lines 41–84)

`toLower` delegates to `toLowerField` so case handling is defined once.
`containsCI` is the case-insensitive substring test behind `SEARCH`.

`splitLine(line, delim, quoted)` (59–84) is one splitter serving both formats.
With `quoted = true` it handles RFC-4180 CSV — quoted fields, embedded
delimiters, and `""` as an escaped quote. With `quoted = false` it does a plain
split, which is what UniProt's TSV needs (tab-separated, never quoted).

### Filtering (lines 100–155)

`matchCondition` branches on whether the attribute is numeric. For `length` it
compares as `double`; for everything else `=`/`!=` are case-insensitive exact
matches. The ordering operators are unreachable for strings because semantic
analysis rejects them — but the code still handles them with a lexicographic
comparison rather than returning `false`, so skipping the semantic phase would
degrade gracefully instead of lying.

`matchWhere` is the DNF evaluator, and it is four lines of logic: for each
AND-group, if every condition matches, the record matches. An empty `WHERE`
matches everything.

`matchSearch` scans all six attributes via `proteinFields()` — including
`sequence`, which is what makes `SEARCH "MVLSPADK"` a motif search.

### UniProt (lines 159–262, 340–430)

**`urlEncode` (159–178)** percent-encodes everything outside RFC 3986's
unreserved set. This is deliberately more aggressive than necessary for
correctness, because the encoded URL is interpolated into a shell command:
after encoding, a query containing `&`, `|`, backticks or quotes contains only
`[A-Za-z0-9-_.~%]`, so it cannot become shell syntax. Combined with the
lexer's inability to produce a string containing `"`, the injection surface is
closed twice over.

**`hashHex` (181–190)** is FNV-1a, used only to name a cache file per URL. It
is compiled out of the browser build, which caches in memory and needs no
filename.

**`cleanFunction` (196–221)** strips the leading `FUNCTION: ` and any
`{ECO:...}` evidence blocks from UniProt's annotation text, then collapses the
whitespace left behind. Metadata removal, not data alteration — every other
field is passed through verbatim.

**`parseUniProtStream` (223–253)** parses the TSV from any `std::istream`,
which is what lets the native build read a cached file and the browser build
read an in-memory string with the same code.

**`loadUniProt` (340–430)** is the one genuinely forked function:

```cpp
#ifdef __EMSCRIPTEN__
    // browser: js_fetch_text(), in-memory cache
#else
    // native: curl via std::system(), .cache/ on disk
#endif
```

The browser branch calls `js_fetch_text`, declared at the top of the file with
`EM_ASYNC_JS` (lines 26–34) — a JavaScript function callable from C++ that
`await`s `fetch()`. Emscripten's ASYNCIFY transform suspends the WebAssembly
stack across that `await` and resumes it when the promise settles, which is
why `loadUniProt` can stay an ordinary synchronous function on both sides.

The native branch builds a `curl` command, writes to a `.part` file, renames
on success, and parses. Both branches discard a response that yielded zero
records, so a transient empty result can't get stuck in the cache.

> **Reviewer question — "why `curl` and not libcurl?"** Linking libcurl means
> finding and shipping a dependency on three platforms. `curl` the executable
> is already present on Windows 10+ and every mainstream Linux distribution,
> so the compiler stays dependency-free. The cost is a process spawn per
> query, which is irrelevant next to the network round-trip.

### `loadDataset` (289–338)

Opens the file, skips the header, splits each row, and requires six columns.
`Length` is converted with `std::stoi` inside a `try`, so a malformed number
becomes a clean runtime error naming the line rather than an exception
escaping. Trailing `\r` is stripped, so a CSV written on Windows loads on
Linux and vice versa.

### `runQuery` (432–493)

The heart of Phase 4, and deliberately short:

```cpp
std::vector<const ProteinRecord*> hits;   // pointers, not copies
```

1. **Filter** — one pass, keeping pointers to matching records.
2. **Sort** — `std::stable_sort`, numeric for `length` and case-insensitive
   text otherwise. Stability means equal keys keep dataset order, so results
   are reproducible.
3. **Truncate** — `hits.resize(topN)`.
4. **Project** — build `columns` from `DISPLAY` (or all six), then materialise
   the rows. `COUNT` returns before materialising anything, since it only
   needs the size.

Working with `const ProteinRecord*` means sorting moves pointers rather than
whole records — each of which contains a full amino-acid sequence.

### `printResult` (495–554)

Renders the aligned text table: measure every column, print a rule, print
headers, print rows, print a rule, then the row count. Long values are elided
at 40 characters **in the text renderer only** — `--json` always emits the
full value, so the browser can show a complete sequence.

## The driver — `pipeline.h`, `pipeline.cpp`

254 lines. The phase sequence, written once.

### `pipeline.h`

```cpp
enum class Stage { Parse, Semantic, Runtime, Done };

struct PipelineOutput {
    bool ok; Stage stage; size_t statements; std::string astText;
    std::vector<std::string> errors, sources; std::vector<QueryResult> results;
};
```

`Stage` is how a caller distinguishes "your query has a typo" from "UniProt is
unreachable" — it becomes the `stage` field in the JSON and the exit code on
the command line.

### `runPipeline` (lines 69–169)

```cpp
PipelineOutput runPipeline(const ExecOptions& opts,
                           std::ostream* report,
                           const std::string& sourceLabel);
```

The `report` parameter is the trick that lets one function serve both output
modes. Pass `&std::cout` and it narrates each phase as it happens, which is
what the CLI wants — including live progress before a slow UniProt fetch. Pass
`nullptr` and it runs silently, and the caller renders `PipelineOutput` as
JSON. Neither mode is a reimplementation of the other.

The body is the four phases in order:

1. `yyparse()`, then `printProgram` into a string — **the AST is captured even
   when a later phase fails**, so the web page can show what was parsed next to
   the errors. Bail if `parseResult != 0 || lex_errors > 0`.
2. `validateProgram`. Bail with `Stage::Semantic`.
3. Execution: walk the statements, `LOAD` replacing `records` and `FIND`
   appending a `QueryResult`.
4. Set `ok`/`Stage::Done`.

Note what the caller must do *before* calling: point the lexer at its input.
That is the single line of difference between the two front ends.

### `resetPipelineState` (62–67)

```cpp
g_program.clear(); g_parseErrors.clear(); lex_errors = 0; yylineno = 1;
```

The CLI runs one program per process and would not need this. The wasm module
runs many per page load, and Bison's state is global — without this reset, the
second query would see the first query's statements. This is the kind of bug
that only appears in the long-lived build.

### `toJson` (171–200)

Serialises `PipelineOutput` by hand — no JSON library, one more dependency
avoided. Every string goes through `jsonEscape` (in `executor.cpp`), which
handles quotes, backslashes, control characters and `\uXXXX` escapes. This
matters because UniProt's function text is arbitrary prose arriving over the
network.

## Front end 1 — `main.cpp`

102 lines: parse arguments, point the lexer, choose an output mode.

`parseArgs` (42–61) handles `--json`, `--cache-dir`, and one positional path.
A path of `-` means stdin, which is why `- ` is excluded from the "unknown
option" check.

`main` (64–102):

```cpp
yyin = fromStdin ? stdin : std::fopen(path, "r");
resetPipelineState();
const PipelineOutput out =
    runPipeline(opts.exec, opts.json ? nullptr : &std::cout, opts.sourcePath);
if (opts.json) std::cout << toJson(out) << "\n";
return exitCodeFor(out);
```

That is the entire program. Setting `yyin` is Flex's documented way to choose
an input stream. `exitCodeFor` maps the stage to `0/2/3/4` so scripts and CI
can tell what failed without parsing text.

## Front end 2 — `wasm_api.cpp`

53 lines: the browser's `main`.

```cpp
extern YY_BUFFER_STATE yy_scan_string(const char* str);
extern void yy_delete_buffer(YY_BUFFER_STATE buffer);
```

There is no `stdin` in a browser, so instead of setting `yyin` this front end
uses Flex's string-buffer interface: `yy_scan_string` makes the lexer read
from a JavaScript-supplied string.

```cpp
EMSCRIPTEN_KEEPALIVE
const char* proteindsl_run_json(const char* source) {
    static std::string output;
    ExecOptions opts;
    resetPipelineState();
    YY_BUFFER_STATE buffer = yy_scan_string(source ? source : "");
    const PipelineOutput out = runPipeline(opts, nullptr, "<browser>");
    yy_delete_buffer(buffer);
    output = toJson(out);
    return output.c_str();
}
```

`EMSCRIPTEN_KEEPALIVE` stops the linker discarding a function nothing in C++
calls. The result is held in a `static std::string` and returned as
`const char*`, so JavaScript never has to free anything — the buffer simply
stays valid until the next call.

Compare this to `main.cpp`: same `resetPipelineState`, same `runPipeline`,
same `toJson`. Only the lexer's input differs.

## Build — `Makefile`

99 lines, two builds.

### Native (lines ~26–61)

```make
CORE := ast.cpp semantic.cpp executor.cpp pipeline.cpp
SRCS := $(CORE) main.cpp
```

`CORE` is everything except the front end, so the wasm target can reuse it
verbatim.

The generation rules encode the real dependency order:

```make
$(BUILD)/parser.tab.cpp $(BUILD)/parser.tab.hpp: parser.y
	bison -d -o $(BUILD)/parser.tab.cpp parser.y

$(BUILD)/lexer.yy.cpp: lexer.l $(BUILD)/parser.tab.hpp
	flex -o $(BUILD)/lexer.yy.cpp lexer.l
```

Bison's `-d` emits the header of token constants; the lexer rule depends on
that header, because `lexer.l` includes it. Get this dependency wrong and a
clean parallel build fails intermittently.

`run-invalid` is prefixed with `-`, because that sample is *supposed* to exit
3 and Make would otherwise report the expected failure as a build error.

### WebAssembly (lines ~63–89)

```make
EMFLAGS := -std=c++17 -O2 -I. -I$(BUILD) \
	-sASYNCIFY \
	-sMODULARIZE -sEXPORT_NAME=createProteinDSL \
	-sALLOW_MEMORY_GROWTH \
	-sEXPORTED_FUNCTIONS=_proteindsl_run_json,_malloc,_free \
	-sEXPORTED_RUNTIME_METHODS=ccall,UTF8ToString,stringToNewUTF8 \
	--preload-file dataset
```

Each flag earns its place:

| Flag | Why |
|------|-----|
| `-sASYNCIFY` | Lets `LOAD UNIPROT` await a `fetch` from inside C++ |
| `-sMODULARIZE` + `EXPORT_NAME` | Exposes a `createProteinDSL()` factory instead of polluting globals |
| `-sALLOW_MEMORY_GROWTH` | A 500-entry UniProt response with sequences can be megabytes |
| `EXPORTED_FUNCTIONS` | Keeps the entry point (leading `_` is the C symbol prefix) |
| `EXPORTED_RUNTIME_METHODS` | `ccall` to invoke it; the string helpers are used by `EM_ASYNC_JS` |
| `--preload-file dataset` | Puts `dataset/proteins.csv` in the virtual filesystem |

The target is `em++`, not `emcc` — `emcc` links as C and the build fails with
hundreds of undefined `std::` symbols.

## The page — `web/`

### `index.html` (81 lines)

Plain semantic markup: a textarea, a Run button, an examples row, a language
reference, and panels for output and the AST. Two script tags at the end:

```html
<script src="proteindsl.js" defer></script>
<script src="app.js" defer></script>
```

Order matters — `defer` preserves document order, so the module has defined
`createProteinDSL` before `app.js` runs. There are **no inline styles or
scripts anywhere**, which is what allows a strict `default-src 'self'` policy.

### `app.css` (101 lines)

CSS custom properties for the palette, a two-column grid collapsing to one
below 900px, and `overflow-x: auto` on the table wrapper so wide result sets
scroll inside their panel instead of stretching the page.

### `app.js` (165 lines)

```js
const wasmModule = createProteinDSL();

async function execute(source) {
  const mod = await wasmModule;
  const json = await mod.ccall(
    "proteindsl_run_json", "string", ["string"], [source], { async: true });
  return JSON.parse(json);
}
```

That is the entire backend. `{ async: true }` is required: because of
ASYNCIFY the exported function may suspend, so `ccall` returns a promise.

`renderResult` (39–100) builds the results table with `createElement` and
**`textContent`, never `innerHTML`** — the values are arbitrary text arriving
from UniProt, and `textContent` cannot be induced to execute markup.

`render` (102–132) draws errors, the source line, each result block, and the
status. `run` (134–147) disables the button, awaits `execute`, and always
re-enables in a `finally`.

## Tooling and CI

### `tools/make_examples.py` (38 lines)

Reads every `.dsl` in `sample_queries/` and writes `docs/examples.json`.
Generating the list rather than hardcoding it in `app.js` is what keeps the
playground's examples identical to the repository's samples.

### `.github/workflows/pages.yml` (90 lines)

On every push to `main` touching source, the page or the workflow:

1. `apt-get install flex bison`.
2. Restore Emscripten from cache, keyed on the **pinned** version — a ~650 MB
   download otherwise.
3. `make wasm PYTHON=python3`, then assert the outputs are non-empty.
4. `make` and run `valid_query.dsl`, grepping for an expected row — so a
   change that breaks the native front end cannot deploy green.
5. Upload `docs/` and deploy to Pages.

The workflow is why `docs/` is gitignored: the site is rebuilt from source on
every push, so no compiled artefact is ever committed.

### `.gitignore`

Ignores `build/`, `bin/`, `docs/`, `.cache/`, and in-tree flex/bison output.
Everything ignored is reproducible from source with one `make`.
